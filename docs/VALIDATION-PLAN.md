# Controlled End-to-End Validation Plan

**Status:** **NO-GO as of September 7, 2026**

The current Sentinel workspace has useful upstream and downstream evidence, but
it does not yet have the native Foundry and MCP-host telemetry required for a
valid end-to-end validation. No test mutation may be executed until every
required GO item in this document is satisfied.

## 1. Purpose and scope

This plan validates whether TraceBack can reconstruct the following chain from
telemetry already generated by the participating platforms:

1. Human test operator
2. Microsoft 365 Copilot agent
3. Microsoft Foundry agent
4. MCP service hosted in Azure Functions or Azure Container Apps
5. Workload identity or delegated token subject
6. Microsoft Graph action
7. Harmless disposable target

TraceBack is a separate, local, read-only investigation application. It must
not be inserted into the execution path and must not write telemetry, modify
the agents, or influence the request.

This plan does **not** authorize:

- Changes to the Microsoft 365 Copilot agent, Foundry agent, MCP application
  code, Graph request construction, or Graph SDK behavior.
- Custom correlation headers, custom correlation IDs, test-only span
  attributes, custom audit records, or additional application logging.
- Prompt, response, token, or request-body capture solely for this test.
- Testing against a real user's account, mailbox, files, group memberships, or
  privileges.
- Public or shared deployment of TraceBack. `SECURITY.md` remains authoritative;
  use TraceBack only from its approved isolated, loopback-only environment.

## 3. Evidence and attribution standard

The operator's worksheet is ground truth for evaluating TraceBack; it must
never be used as input evidence by TraceBack.

An adjacent hop is linked only when the platform telemetry shares an exact
platform-generated identifier, such as a request, operation, trace, span,
token, session, conversation, thread, message, or task identifier. A stable
actor/application/resource identifier may support a candidate relationship,
but actor plus time alone is not attribution.

The application uses a five-minute adjacent-event window. It rejects events
more than 30 seconds out of order and does not resolve ties by row order.
Therefore:

- All participating systems must have synchronized UTC time.
- Only one validation invocation may be active at a time.
- No other action may write to the selected disposable target during the
  seven-day TraceBack search window.
- Operator timestamps narrow manual review; timestamps do not replace an exact
  join key.
- Application-permission activity identifies the workload identity, not the
  human, unless the upstream human-to-workload chain is independently linked.

### Expected Sentinel evidence by hop

| Hop | Required Sentinel evidence | Key fields |
|---|---|---|
| H1: Human | `CopilotActivity`; `SigninLogs` or `AADNonInteractiveUserSignInLogs` as corroboration | `RecordId`, `ActorUserId`, request/session/conversation/message identifiers, UTC time |
| H2: Microsoft 365 Copilot agent | `CopilotActivity` from the same interaction | `AgentId`, `AppIdentity`, `ConversationId`, `ThreadId`, message/task identifiers |
| H3: Foundry agent | Primarily `AppRequests`; related `AppDependencies`, `AppTraces`, `AppEvents`, or `AppExceptions` | `OperationId`, `Id`, `ParentId`, trace/span IDs, `gen_ai.agent.id`, conversation ID, Foundry resource |
| H4: MCP service | An allowlisted `AppRequests`, `AppDependencies`, or `AppTraces` record classified as an MCP tool call | Accepted operation name plus operation/trace/span lineage; native `FunctionAppLogs` or `ContainerAppHTTPLogs` is manual corroboration only |
| H5: Identity/token subject | Delegated: `AADNonInteractiveUserSignInLogs`; application: `AADServicePrincipalSignInLogs` or `AADManagedIdentitySignInLogs` | `UniqueTokenIdentifier`, `OriginalRequestId`, user ID or app/service-principal ID, successful result |
| H6: Microsoft Graph action | `MicrosoftGraphActivityLogs` | `RequestId`, `ClientRequestId`, `OperationId`, `SignInActivityId`, permission claims, method, status, URI |
| H7: Disposable target | The same successful `MicrosoftGraphActivityLogs` row; optional `AuditLogs` target corroboration | Exact target object ID in the Graph URI; audit target ID/type when present |

`AzureActivity` can prove changes to Azure resources or diagnostics, but it
does not prove the directory data-plane `PATCH /groups/{id}` action.

## 4. Required platform-only telemetry onboarding

All onboarding in this section is an administrative prerequisite performed by
authorized resource owners before the GO decision. It is configuration of
native platform diagnostics or data connectors, not custom application
instrumentation.

### 4.1 Common destination

Use the existing Sentinel-enabled Log Analytics workspace as the common query
destination.

- Create or select a **workspace-based Application Insights component** whose
  backing Log Analytics workspace is the Sentinel workspace.
- Do not use a classic Application Insights component or an Application
  Insights component backed by a different workspace; the current TraceBack
  adapter queries one explicit workspace and does not perform cross-resource
  queries.
- A single dedicated validation Application Insights component may be shared
  by Foundry and the Function host if policy permits. Separate components are
  acceptable only when both write to the same Sentinel workspace.
- Do not redirect an existing production component if doing so would interrupt
  current monitoring. Use a preapproved validation deployment or defer the
  test.

### 4.2 Microsoft Foundry

Connect the workspace-based Application Insights component to the exact
Foundry project used by the investigated agent.

Foundry server-side tracing begins after the project is connected and requires
no agent code changes. Do not enable optional message-content capture for this
test. The minimum required result in the Sentinel workspace is:

- A new `AppRequests` row for an invocation, with a usable `OperationId` and
  `Id`.
- A Foundry-identifying value in the allowed projection, preferably
  `Properties["gen_ai.agent.id"]`, and an invocation operation such as
  `invoke_agent` or `gen_ai.invoke_agent`.
- Child dependency or trace records that preserve `OperationId`, `Id`, and
  `ParentId` sufficiently to connect the agent invocation to its MCP tool call.

`AppGenAIContent` may also appear, but it is not required and is not queried by
the current TraceBack implementation. Do not broaden access merely to inspect
prompt or response content.

### 4.3 MCP host: Azure Functions path

**Recommended first test path:** Azure Functions, because its native
Application Insights integration can populate the `App*` tables already
allowlisted by TraceBack.

Enable the Function App's built-in Application Insights integration against a
workspace-based component backed by the Sentinel workspace. This is a platform
configuration change; do not add an SDK, middleware, headers, log statements,
or test-only settings to the function code.

The minimum acceptable evidence is:

- A request record for the MCP invocation in `AppRequests`.
- If the platform automatically collects the outbound Graph dependency, a
  corresponding `AppDependencies` row.
- Platform-generated `OperationId`, `Id`, and `ParentId` values that connect
  the request/dependency to the Foundry trace.
- A normalized operation name accepted by the current TraceBack implementation
  for hop 4: `tools/call`, `mcp.tool.call`, or `mcp.tools.call`.

A diagnostic setting that sends `FunctionAppLogs` to the Sentinel workspace is
permitted as a native fallback for manual diagnosis. It does not, by itself,
make the current TraceBack application ready because `FunctionAppLogs` is not
in its query allowlist.

If the Function App already uses an Application Insights component backed by a
different workspace, do not silently repoint it. The test remains NO-GO until
an approved validation deployment or approved same-workspace telemetry path is
available.

### 4.4 MCP host: Azure Container Apps path

At the Container Apps managed-environment level:

- Set the log destination to Azure Monitor or Log Analytics as appropriate for
  the approved design.
- Enable the native diagnostic categories
  `ContainerAppHTTPLogs`, `ContainerAppSystemLogs`, and
  `ContainerAppConsoleLogs` to the Sentinel workspace. HTTP logs are opt-in and
  are required to observe ingress method, path, status, latency, revision, and
  the platform request ID.
- Do not add console logging or OTel instrumentation to the MCP application.

The current TraceBack implementation does not query the resulting
`ContainerAppHTTPLogs`, `ContainerAppSystemLogs_CL`, or
`ContainerAppConsoleLogs` tables. Therefore the Container Apps path is
**NO-GO for a complete TraceBack validation** unless an already-existing
platform Application Insights/OTel path also produces compatible `AppRequests`
or `AppDependencies` rows with the required operation names and exact join
keys. Native Container Apps tables alone can support a manual platform
coverage check, not a complete TraceBack pass.

### 4.5 Hosting selection recommendation

Use the **Azure Functions path for the first authorized run** because its
built-in Application Insights integration can produce the `App*` tables that
the current TraceBack query plans already allowlist.

Use the Container Apps path only if pre-GO sample telemetry proves that an
already-existing platform path also emits compatible `AppRequests` or
`AppDependencies` records with the accepted MCP operation name and exact
adjacent-hop keys. Otherwise select Functions or remain NO-GO; do not add
instrumentation merely to make the Container Apps path pass.

### 4.6 Microsoft Entra and Microsoft Graph

Retain or configure Microsoft Entra diagnostic settings to route these
categories to the same Sentinel workspace:

- `SignInLogs`
- `NonInteractiveUserSignInLogs`
- `ServicePrincipalSignInLogs`
- `ManagedIdentitySignInLogs` when the MCP host uses managed identity
- `AuditLogs`
- `MicrosoftGraphActivityLogs`

For Graph-to-sign-in correlation, the critical native join is:

```text

    =
<sign-in table>.UniqueTokenIdentifier
```

The fresh test action must retain `RequestId`, `ClientRequestId`, `OperationId`,
`AppId`, `ServicePrincipalId`, `UserId`, `Scopes`, `Roles`, method, status, URI,
and timestamp in `MicrosoftGraphActivityLogs`.

### 4.7 Microsoft 365 Copilot

- Confirm Microsoft Purview Audit is enabled.
- Retain the existing ingestion path that is populating `CopilotActivity` in

- Confirm that a fresh, non-sensitive interaction produces a

## 6. Pre-GO telemetry probes

Run these queries manually in the Sentinel workspace against a narrow interval
containing known, non-mutating existing traffic. Replace placeholders locally;
do not save identifiers in this repository.

### 6.1 Foundry and MCP `App*` coverage

```kusto
let _start = datetime(<UTC-start>);
let _end = datetime(<UTC-end>);
union withsource=Source
    AppRequests,
    AppDependencies,
    AppTraces,
    AppEvents,
    AppExceptions
| where TimeGenerated between (_start .. _end)
| extend
    TraceId = tostring(Properties["trace_id"]),
    SpanId = tostring(Properties["span_id"]),
    AgentId = tostring(Properties["gen_ai.agent.id"]),
    ConversationId = tostring(Properties["gen_ai.conversation.id"])
| project
    Source,
    TimeGenerated,
    OperationName,
    Name,
    OperationId,
    Id,
    ParentId,
    TraceId,
    SpanId,
    AgentId,
    ConversationId,
    AppRoleName,
    _ResourceId
| order by TimeGenerated asc
```

Do not project the complete `Properties` bag.

### 6.2 Function host coverage

```kusto
let _start = datetime(<UTC-start>);
let _end = datetime(<UTC-end>);
FunctionAppLogs
| where TimeGenerated between (_start .. _end)
| where AppName == "<function-app-name>"
| project
    TimeGenerated,
    AppName,
    FunctionName,
    FunctionInvocationId,
    ActivityId,
    Category,
    Level,
    _ResourceId
| order by TimeGenerated asc
```

This query proves native host logging only. A GO for the current TraceBack
implementation still requires compatible `AppRequests` or `AppDependencies`.

### 6.3 Container Apps host coverage

```kusto
let _start = datetime(<UTC-start>);
let _end = datetime(<UTC-end>);
ContainerAppHTTPLogs
| where TimeGenerated between (_start .. _end)
| where ContainerAppName == "<container-app-name>"
| project
    TimeGenerated,
    ContainerAppName,
    RevisionName,
    Method,
    Path,
    StatusCode,
    RequestId,
    RequestDuration
| order by TimeGenerated asc
```

Do not project `XForwardedFor`. This query proves native ingress logging only;
the table is not currently consumed by TraceBack.

### 6.4 Graph-to-sign-in join

```kusto
let _start = datetime(<UTC-start>);
let _end = datetime(<UTC-end>);
MicrosoftGraphActivityLogs
| where TimeGenerated between (_start .. _end)
| where RequestUri has "<disposable-target-object-id>"
| join kind=leftouter (
    union
        SigninLogs,
        AADNonInteractiveUserSignInLogs,
        AADServicePrincipalSignInLogs,
        AADManagedIdentitySignInLogs
    | where TimeGenerated between (_start .. _end)
) on $left.SignInActivityId == $right.UniqueTokenIdentifier
| project
    GraphTime = TimeGenerated,
    RequestId,
    ClientRequestId,
    OperationId,
    SignInActivityId,
    AppId,
    ServicePrincipalId,
    UserId,
    Scopes,
    Roles,
    RequestMethod,
    ResponseStatusCode,
    RequestUri,
    SignInTime = TimeGenerated1,
    SignInTokenId = UniqueTokenIdentifier,
    SignInResult = ResultType
| order by GraphTime asc
```

The query result is sensitive investigation material. Review it in place and
record only the necessary identifiers in the approved external worksheet.

## 7. Test target and action

Use a different disposable target for each permission mode.

**Target:** An empty, cloud-only Microsoft Entra security group created solely
for validation.

**Action:** One `PATCH /groups/{group-object-id}` request that changes only the
group's `description`.

**Baseline description:** `TraceBack validation baseline`

**Temporary description:** `TraceBack validation active`

**Rollback:** Restore the exact pre-test description captured by the operator.
Do not change display name, membership, owners, role assignability, mail
settings, labels, dynamic rules, or any authorization-related property.

The target object ID is a native resource identifier, not a custom correlation
ID. Do not add a run ID, timestamp, operator name, or random marker to the
description, prompt, headers, or request body.

The target remains in the temporary state until TraceBack evidence is captured.
This avoids creating a second matching Graph write inside the investigation
window. If an emergency rollback is required earlier, roll back immediately,
mark the run invalid, and use a different clean target for any later rerun.

- Use a dedicated, nonprivileged test user, not a real user's normal account.
- The delegated path is already configured end to end; do not change it for
  this test.
- The token used by the MCP service has the minimum preapproved delegated Graph

- The test user is authorized to modify only the selected disposable target
  through the established test controls.
- The delegated target passes the seven-day quiet-target check.

### Script

1. Start the reserved quiet window. Confirm the target description exactly
   matches the recorded baseline and record `T0`.
2. Open Microsoft 365 Copilot as the dedicated test user and select the
   investigated Copilot agent.
3. Record native conversation, thread, and message identifiers exposed by the

7. Independently read the group and record `T3`. The only accepted state change

8. Wait for native telemetry ingestion. Query at approximately T+5 minutes,

## 11. Pass and fail criteria

Classify each scenario independently.

### PASS-E2E

All of the following must be true:

- The intended description changed once and only the intended property changed.
- Rollback restored the exact original value.
- Every required query succeeded without truncation.
- All seven hops are observed.
- All six adjacent links are `linked`, not `candidate`, `unresolved`, or
  `unavailable`.
- Exact key types are reported for every link.
- The selected permission mode matches Graph evidence.
- Delegated mode preserves the same user from H1/H5 through H6.
- Application mode identifies the workload at H5/H6 and independently links
  the original human through H1-H5.
- TraceBack returns `status = complete`,
  `human_attribution = supported`, and no reason codes indicating incomplete,
  ambiguous, contradictory, mixed, or unknown evidence.
- No raw identifiers, UPNs, prompts, request bodies, tokens, dynamic property
  bags, or raw CLI errors appear in the browser or application logs.

### PASS-SAFETY-ONLY

Use this classification when the controlled action and rollback succeeded, but
native telemetry lacks an exact identifier required for one or more links, and
TraceBack correctly returns `partial`, `unresolved`, or `impossible` with
appropriate evidence-gap or structural reason codes.

This result validates conservative behavior only. It is **not** evidence that
end-to-end attribution is ready, and it must not be reported as PASS-E2E.

### FAIL

Any of the following is a failure:

- TraceBack identifies a human from application-permission activity using only
  ownership, app ID, recency, row order, or timestamp proximity.
- TraceBack returns complete when a required source is unavailable, failed,
  truncated, ambiguous, or missing an exact adjacent-hop join.
- Delegated and application permission modes are confused.
- The wrong user, workload identity, action, or target is selected.
- More than one unexplained target write occurs.
- The action changes any property other than `description`.
- Rollback fails or the original value is unknown.
- A required query failure is presented as no matches.
- Sensitive raw telemetry is exposed or persisted.
- The application is run outside its approved local-only security boundary.

### INVALID RUN

Do not score the run when there was a retry, concurrent target activity, clock
error, early rollback, wrong target, alternate agent/tool route, or unrecorded
manual intervention. Clean up and use a different quiet target for a later
authorized run.

## 12. Missing-telemetry decision tree

1. **No fresh `CopilotActivity`:**
   Verify Purview Audit is enabled and the existing Sentinel ingestion path is
   healthy. Confirm the interaction type is covered. Wait through the approved
   audit-ingestion window, up to 24 hours for this test. If still absent, stop:
   NO-GO.
2. **No Foundry `App*` rows:**
   Verify the Foundry project is connected to the workspace-based Application
   Insights component backed by the Sentinel workspace. Confirm a post-link
   invocation appears in Foundry's native Traces view. If it appears there but
   not in the Sentinel workspace, the component/workspace binding is wrong.
   Stop: NO-GO.
3. **Foundry rows exist but agent or invocation fields are absent:**
   Inspect only the allowlisted projected fields. If the current query plan
   cannot classify H3 without code or instrumentation changes, stop: NO-GO
   under this plan.
4. **No MCP host rows:**
   For Functions, verify built-in Application Insights integration and inspect
   `FunctionAppLogs`. For Container Apps, verify managed-environment HTTP log
   diagnostics and inspect `ContainerAppHTTPLogs`. If only native fallback
   tables have data and no compatible `App*` row exists, manual host coverage
   is present but current TraceBack coverage is not. Stop: NO-GO for PASS-E2E.
5. **MCP rows exist but operation name is not recognized:**
   Do not rename the operation or add a test log. The current implementation
   cannot normalize H4. Stop: NO-GO pending a separately reviewed product
   change.
6. **No delegated sign-in row:**
   Verify `NonInteractiveUserSignInLogs` is routed and that the Graph request
   actually used a delegated token. If Graph has `Roles` instead of `Scopes`,
   the scenario used application permissions and is invalid.
7. **No workload sign-in row:**
   Query both service-principal and managed-identity tables and verify the
   configured identity type. Do not infer identity from the resource owner.
8. **No Graph row:**
   Verify the `MicrosoftGraphActivityLogs` diagnostic category and target
   tenant, then wait up to two hours. If the target changed but no row arrives,
   fail telemetry coverage and roll back.
9. **Rows exist but `SignInActivityId` does not join:**
   Record an evidence gap. Do not substitute nearest timestamp or app ID.
10. **Rows exist for every hop but an adjacent exact key is absent:**
    Expect TraceBack to return unresolved or impossible. Classify only as
    PASS-SAFETY-ONLY if it avoids false attribution.
11. **Multiple candidate rows exist:**
    Do not choose the first or closest row. Mark the run invalid or ambiguous.
12. **Sensitive content appears in trace data:**
    Stop investigation, restrict access, follow the organization's incident and
    privacy process, and do not copy the content into the worksheet.

## 13. Safety, privacy, RBAC, cost, and cleanup

### Safety

- Use dedicated test identities and two disposable groups with no business
  dependencies.
- Reserve a quiet window and execute exactly one action per scenario.
- Have an independent rollback operator available.
- Set a maximum rollback deadline of 24 hours after `T1`, even if telemetry is
  still missing.
- Never test a password reset, account disablement, role assignment, membership
  change, credential operation, Conditional Access change, mailbox action, or
  real-user resource.

### Privacy

- Use object IDs rather than UPNs in queries and notes where practical.
- Project only the fields listed in this document.
- Do not export complete `Properties`, `LLMEventData`, request bodies, prompts,
  responses, claims, tokens, URLs with secrets, or IP addresses.
- Keep the operator worksheet access-controlled and delete it according to the
  approved validation retention period.
- TraceBack output must remain sanitized and response-local as required by
  `SECURITY.md`.

### RBAC

- **Telemetry configuration owner:** Only the role holders authorized to create
  diagnostic settings, connect Application Insights, and select the destination
  workspace.
- **Foundry configuration owner:** Sufficient project and Application Insights
  permissions to connect the existing component.
- **Investigator:** `Log Analytics Reader` on the target workspace; add
  `Privileged Monitoring Data Reader` only if protected tables require it.
- **Entra diagnostic owner:** A role authorized to configure Entra diagnostic
  settings; Microsoft documents Security Administrator as the least privileged
  supported admin role for that operation.
- **Delegated test user:** Dedicated nonprivileged account with only the
  preapproved delegated Graph access and target authorization.
- **Application test identity:** Dedicated service principal or managed identity
  with only the preapproved application permission. Remove temporary consent or
  assignment after the test.
- **TraceBack runtime identity:** Read-only access to the explicit Sentinel
  workspace and resource metadata only.

No validation operator should hold both unrestricted Graph write authority and
unreviewed telemetry administration unless required by the organization's
separation-of-duties policy.

### Cost

- Expected workload is two agent invocations, two Graph writes, two rollbacks,
  and bounded telemetry queries.
- Application Insights, Log Analytics ingestion/retention, Copilot usage, and
  Foundry/model/tool calls can incur charges.
- Use one attempt per scenario, narrow manual query windows, projected columns,
  and bounded results.
- Do not enable verbose content capture, broad debug logs, or repeated polling.
- Review the destination workspace's retention and daily-cap policies before
  GO; a cap that can drop validation telemetry is a NO-GO.

### Cleanup

After each scenario:

1. Restore the exact original target description and verify it independently.
2. Record the rollback Graph request and time separately from the test action.
3. Revoke test-only delegated consent, application consent, role assignment, or
   ownership that was explicitly approved as temporary.
4. Leave shared production identities and diagnostic settings unchanged unless
   the change owner has an approved rollback for the telemetry onboarding.
5. Delete the disposable groups only after evidence review and outside the
   seven-day investigation window, or retain them disabled from all business
   use for repeatable validation according to policy.
6. Remove screenshots and raw exports; retain only the approved sanitized
   evidence record and decision.
7. Record costs and any ingestion delay that affected the run.

## 14. Concise GO/NO-GO decision

**GO only when every statement is true:**

- [ ] Security approval permits local TraceBack execution.
- [ ] The disposable target, rollback owner, quiet window, and test identities
  are approved.
- [ ] Foundry server-side traces reach `App*` tables in the Sentinel workspace.
- [ ] The selected MCP host produces native telemetry in the same workspace.
- [ ] The current TraceBack allowlist recognizes both H3 and H4 rows.
- [ ] Sample telemetry proves an exact native join key for every adjacent edge.
- [ ] Copilot, Entra sign-in, Graph activity, and target audit sources are fresh.
- [ ] Delegated and application permissions are independently verified.
- [ ] Read-only investigator RBAC and privacy controls are in place.
- [ ] No required source is capped, sampled away, inaccessible, or over the
  100-row TraceBack limit.
- [ ] The stop, rollback, retention, and cost owners have accepted the run.

**NO-GO if any statement is false.** In particular, the currently absent
Foundry/MCP telemetry and missing Application Insights-to-Sentinel linkage must
be resolved and proven before either Graph mutation scenario is executed.
